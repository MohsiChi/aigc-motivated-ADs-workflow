**看图要点**

## 图 2｜一个任务的一生（含返工与被拦截）

回答：**"数据怎么流？什么时候会失败？"** 实线是主路径，右侧分支是拦截路径。

```mermaid
flowchart TD
    S0["调用方 POST /tasks<br/>topic + product_info + scene_count"]
    S1["落库 status=PENDING<br/>写 task_events"]
    S2["入进程内队列<br/>立即返回 202 + task_id"]
    S3{"Worker 取到任务<br/>当前还是 PENDING？"}
    S4["跳过<br/>幂等保护：同一任务只执行一次"]
    S5["置 RUNNING<br/>状态最后写的契约开始生效"]

    P1["script → Storyboard 分镜表"]
    P1b["按分镜初始化每个镜头的状态机"]
    P2["prompt → PromptPack 逐镜指令 中英双语"]
    P2b["镜头们 PENDING → GENERATING"]
    P3["generation → clips 素材清单<br/>Tool Calling：先关键帧，再图生视频"]
    P3b["镜头们 GENERATING → IN_REVIEW"]
    P4["review → ReviewReport<br/>逐镜 verdict + findings 六条规则"]
    P4b["按裁决给镜头盖 ACCEPTED / REJECTED"]

    G{"交付门禁<br/>有 BLOCKER 且 repair_policy 里没有修复通道？"}
    X1["相关镜头 → BLOCKED<br/>写 warning + event"]
    X2["抛 StepFailure<br/>任务 status=FAILED"]
    X3["导出失败审计包<br/>00_task.json 带终态与镜头状态<br/>不产出 final.mp4"]

    R1{"还有 REJECTED 镜头<br/>且重试额度未用完？"}
    R2["只重做这些镜头<br/>generation → review 再判一轮<br/>attempt + 1"]
    R3["重试耗尽<br/>REJECTED → ACCEPTED_FALLBACK<br/>逐个告警，不阻塞整片"]

    P5["compose → final.mp4<br/>字幕 + 推近 + 淡入淡出"]
    O1["置 SUCCEEDED<br/>再导出交付包"]
    O2["调用方 GET /tasks/:id<br/>拿状态 + 全部产物 + 留痕"]

    S0 --> S1 --> S2 --> S3
    S3 -->|否| S4
    S3 -->|是| S5 --> P1 --> P1b --> P2 --> P2b --> P3 --> P3b --> P4 --> P4b --> G
    G -->|是| X1 --> X2 --> X3
    G -->|否| R1
    R1 -->|是| R2 --> G
    R1 -->|否| R3 --> P5 --> O1 --> O2
```

**看图要点**

- 顺序是 `script → prompt → generation → review → compose`，中间**没有任何一步知道上一步是谁**，只读 `ctx.artifacts` 里的产物。
- 返工只重跑 `generation` 和 `review`。所以缺陷归属在上游（提示词/分镜）时，返工改变不了裁决——这是目前仍标记为"未修"的那一项。
- 交付门禁在 `compose` **之前**：合规不合格根本不会进入剪辑环节，所以成片里不可能出现违规旁白。
- `00_task.json` 里的 `status` 一定是终态，因为导出发生在状态落定之后（先写状态再导包）。

## 图 3｜双层状态机（合法流转的唯一真相）

回答：**"某个状态还能去哪？"** 图里没有的箭头，代码会在第一现场抛 `IllegalTransitionError`。

```mermaid
stateDiagram-v2
    direction LR
    state "任务级 TaskStatus" as T {
        [*] --> PENDING : 提交任务
        PENDING --> RUNNING : Worker 领取
        PENDING --> FAILED : 启动即失败
        RUNNING --> SUCCEEDED : 走完 compose
        RUNNING --> FAILED : 步骤致命失败 / 门禁拦截
        SUCCEEDED --> [*]
        FAILED --> [*]
    }
```

```mermaid
stateDiagram-v2
    direction LR
    state "镜头级 SceneStatus" as C {
        [*] --> S_PENDING : 由分镜初始化
        S_PENDING : PENDING
        S_PENDING --> GENERATING : 进入生成
        GENERATING --> IN_REVIEW : 生成完毕
        IN_REVIEW --> ACCEPTED : 质检通过
        IN_REVIEW --> REJECTED : 质检不通过
        REJECTED --> GENERATING : 返工 受 MAX_SCENE_RETRIES 限制
        REJECTED --> ACCEPTED_FALLBACK : 非合规类 耗尽后降级采用
        REJECTED --> BLOCKED : 合规类且无修复通道
        ACCEPTED --> [*]
        ACCEPTED_FALLBACK --> [*]
        BLOCKED --> [*]
    }
```

**看图要点**

- 两个终态 `ACCEPTED` / `ACCEPTED_FALLBACK` 表示"可以出货"；`BLOCKED` 表示**不许出货**，且它是从 `REJECTED` 才进得去——不能绕过质检直接拦。
- `ACCEPTED` 是终态、不回退。曾出现"复检说不合格但状态已是 ACCEPTED"的矛盾，那属于数据不一致，现在记告警留痕而不是改状态。
- 状态转移是纯内存组件，落库由 `task_store` 做。**这两者分离正是扩展性问题的来源**，也是它现在只能跑单 Worker 的原因（见 `02-架构设计.md` 演进路线第 8 项）。

## 图 4｜数据契约：谁交出什么、记在哪

回答：**"步骤之间传的东西长什么样？出了问题我查哪张表？"**

```mermaid
flowchart LR
    IN["输入<br/>topic / product_info / scene_count"]
    SB["Storyboard<br/>scenes: Scene 列表<br/>title narration visual duration_s"]
    PP["PromptPack<br/>prompts: ScenePrompt 列表<br/>image_prompt + _en + video_prompt + first_frame_desc"]
    GC["generation 产物<br/>clips: Clip 列表<br/>keyframe_path clip_path attempt provider"]
    RR["ReviewReport<br/>passed_all + rules_version<br/>verdicts: SceneVerdict<br/>└ findings: Finding<br/>rule_id field owner severity"]
    CS["compose 产物<br/>final_video_path scene_videos"]
    OUT["outputs/:task_id<br/>00 元信息 01 脚本 02 提示词<br/>03 关键帧 04 片段 05 质检 06 成片"]

    IN --> SB --> PP --> GC --> RR --> CS --> OUT
    RR -.->|"owner 决定退回哪个工位"| PP
    RR -.->|"BLOCKER 且无修复通道 → 拦截"| OUT
```

```mermaid
erDiagram
    tasks ||--o{ steps : "一个任务有多条步骤记录"
    tasks ||--o{ task_events : "一个任务有多条生命周期事件"
    tasks {
        TEXT id PK
        TEXT status "PENDING/RUNNING/SUCCEEDED/FAILED"
        TEXT current_step
        TEXT warnings "JSON 数组"
        TEXT artifacts "JSON 对象 存上面五个产物"
        TEXT error
    }
    steps {
        INTEGER id PK
        TEXT name "五个步骤名之一"
        TEXT status
        INTEGER attempt "返工轮次 第2/3次会新增行"
        TEXT output "该步产物快照"
        TEXT started_at
        TEXT finished_at
    }
    task_events {
        INTEGER id PK
        TEXT step
        TEXT message "任务开始 返工第N次 门禁拦截 降级采用 导出"
    }
```

**看图要点**

- `steps` 表是**返工是否真的有效**的唯一可靠证据来源。同一 `name` 出现 `attempt=1,2,3` 说明重跑了；`output` 字段里存着那一轮的裁决，把三轮的 `output` 规范化比对即可判断结论有没有变化。
- `artifacts` 是一个 JSON 列，键就是 `storyboard / prompts / generation / review_report / scene_states / compose / export_dir`。**它是整块读改写**，所以并发下会丢更新（演进路线第 3 项要拆它）。
- 虚线两条是本轮加的语义：`Finding.owner` 指向"该退回哪个工位"，BLOCKER 直接决定"能不能出片"。

## 附：当前实现的边界（看图时别误读）

| 图里看起来有 | 实际状态 |
|---|---|
| generation 会重做 | 只重做质检不通过的镜头；缺陷在上游产物时属于无效重做，**已用 1 条 xfail 测试标注未修** |
| providers 三档 | `jimeng` 是**空插座**，未接任何付费视频模型 |
| compose 产出成片 | 真实图档走"直接拼接"分支，**旁白不会烧成字幕**（只测试档生效） |
| 队列 + Worker | 进程内队列，**不支持多 Worker**；进程重启后 PENDING 任务丢失、RUNNING 任务永久卡住 |
| 双层状态机 | 镜头状态存在内存实例上，落库靠另一个对象，两边可能不一致（已通过 F15 修复，但结构未变） |
| 全程留痕 | 有 `warnings`/`00_task.json`，**没有指标聚合接口，也没有成本计量** |

这些都已写在 `README.md` 的「已知限制」里，不是本图新增的坏消息。
